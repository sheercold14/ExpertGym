## 2. Abstract Skeleton

Large language models often acquire specialized abilities through task-specific fine-tuning, producing multiple expert checkpoints or task vectors. A central question is how to combine these experts without retraining the full model or relying on large multi-task corpora. We propose **ExpertGym**, a gate-only calibration framework that learns a small set of task-vector composition coefficients from a compact pool of high-information prompts. Instead of treating calibration as random held-out data, ExpertGym actively identifies prompts whose rewards are sensitive to expert coefficients, making each calibration example informative for coefficient selection. We instantiate ExpertGym on tool use, memory, and code tasks, and optimize expert coefficients with reward feedback while keeping base model parameters frozen. Experiments show that a small, carefully selected calibration pool can recover stronger expert mixtures than random calibration or uniform merging, while revealing trade-offs among competing abilities.

## 3. Motivation

### 3.1 Problem Background

Specialized fine-tuning often creates multiple task experts. For example:

- a tool-use expert improves function calling and tool schema following;
- a memory expert improves evidence aggregation and factual recall over provided memory;
- a code expert improves program synthesis and test passing.

The practical need is not always to train a new model from scratch. Often we already have several useful task vectors and need to decide:

```text
How much of each expert should be merged into the final model?
```

### 3.2 Why Existing Approaches Are Insufficient

| Approach | Limitation for ExpertGym Setting |
|---|---|
| Uniform task vector merging | Assumes all experts should contribute equally |
| Manual grid search | Expensive and does not scale with many experts/layers |
| Large multi-task RL | Learns new behavior but weakens the claim of efficient coefficient selection |
| Random calibration set | Many prompts are all-correct or all-wrong, giving little signal |
| Full parameter update | Hard to attribute gains to expert composition |

### 3.3 Key Observation

Most calibration prompts are low-information for coefficient learning:

```text
If all gate settings solve a prompt, the prompt cannot identify coefficients.
If no gate setting solves a prompt, the prompt also cannot identify coefficients.
Useful prompts are those whose reward changes when expert coefficients change.
```

## 5. Method Overview

### 5.1 Expert Task Vectors

Given a base model parameter vector `theta_0` and task-specific expert checkpoints `theta_tool`, `theta_memory`, `theta_code`, define task vectors:

```text
v_tool   = theta_tool   - theta_0
v_memory = theta_memory - theta_0
v_code   = theta_code   - theta_0
```

The merged model is:

```text
theta(g) = theta_0 + g_tool * v_tool + g_memory * v_memory + g_code * v_code
```

where `g = [g_tool, g_memory, g_code]` are learnable gate coefficients.

### 5.3 Gate-Only Reward Optimization

Base model parameters and expert vectors are frozen. Only gate coefficients are optimized.

For a prompt `x`, sampled response `y`, and reward `R(x, y)`, the optimization objective updates gates so that high-reward samples become more likely under the gated model.

For GRPO-style relative advantage:

```text
A_i = (R_i - mean(R)) / (std(R) + epsilon)
```

Only prompts with reward variance provide strong policy signal.

### 5.4 High-Information Calibration

The central methodological claim is that calibration prompts should be selected for coefficient information, not merely sampled randomly.

We define two useful notions:

#### Policy-Frontier Signal

A prompt is policy-frontier if the current policy sometimes succeeds and sometimes fails:

```text
0 < success_rate(prompt) < 1
reward_std(prompt) > threshold
```

#### Gate-Sensitivity Signal

A prompt is gate-sensitive if different gate probes produce different rewards:

```text
gate_sensitivity(x) = std_g R(theta(g), x)
```

where `g` ranges over a small set of probe gates:

```text
g0, tool+, memory+, code+, conflict directions
```

### 6.3 Proposed Selection Algorithm

Candidate algorithm:

```text
Input:
  candidate prompts D
  expert vectors V = {tool, memory, code}
  probe gates G = {g0, tool+, memory+, code+, conflict probes}
  budget B per task

For each prompt x in D:
  for each probe gate g in G:
    generate K responses from theta(g)
    compute reward statistics

  compute:
    policy_frontier_score(x)
    gate_sensitivity_score(x)
    conflict_score(x)

Select:
  top-B prompts per task under a balanced mixture of these scores
```

Possible score:

```text
score(x) =
  alpha * gate_sensitivity(x)
  + beta * policy_frontier_score(x)
  + gamma * conflict_score(x)
```

## 7. Training Objective

### 7.1 Main Objective

Gate-only GRPO on selected calibration prompts:

```text
maximize E_x,y [ A(x,y) * log p_theta(g)(y | x) ]
```

where only `g` is trainable.

### 7.2 Regularization

Regularize gates toward initial coefficients:

```text
L = L_GRPO + lambda_prior * ||g - g_init||^2
```

For parameter-wise gates:

```text
L = L_GRPO
  + lambda_global * ||g_global - g_global_init||^2
  + lambda_residual * ||r_param - r_param_init||^2
```

### 7.3 Guard Acceptance

After each update:

```text
if guard reward drops below threshold:
  reject or stop
else:
  accept candidate gate
```

## 14. Risks and Reviewer Concerns

### Concern 1: Is this just multi-task RL?

Response:

No. ExpertGym freezes the model and updates only a small number of expert composition coefficients. The method is designed for coefficient identification, not capability learning.

Required evidence:

- number of trainable parameters is tiny;
- same pool size comparison with random calibration;
- no full-model or LoRA update;
- selected prompts are chosen for gate sensitivity.

### Concern 2: Does high calibration reward generalize?

Response:

Need heldout task evaluation and guard retention.

Required evidence:

- external heldout benchmark;
- guard pool;
- random-vs-selected pool comparison;
- overfit gap.

### Concern 3: Are gains due to data selection or just more compute?

Response:

Use equal budget:

```text
same candidate pool
same number of selected prompts
same rollout samples
same gate update steps
```

### Concern 4: Why RL instead of grid search?

Response:

Grid search is feasible only for very low-dimensional global gates. RL/logprob-based optimization can extend to layer-band and parameter-wise gates where grid search is combinatorially expensive.

### Concern 5: What if 588 parameters overfit?

Response:

This is expected under small pools. It motivates staged parameterization:

```text
global for low-data stability
layer-band for structured interaction
global-parameter only when signal is sufficient
```
