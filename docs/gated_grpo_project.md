# Gated-GRPO for OP-VEC task-vector coefficients

## Goal

This branch implements a minimal **Gated-GRPO** loop for the current OP-VEC
project.  The base model and expert task-vector deltas are frozen.  The only
trainable parameters are the OP-VEC gates / task-vector coefficients:

```text
W(alpha) = W_base + sum_i alpha_i * Delta_i
```

The rollout mode is standard on-policy RLVR: use prompt-only calibration data,
let the current gated model sample multiple responses, score responses with the
existing verifier router, and apply a GRPO clipped policy loss to `alpha`.

This is deliberately different from using base/expert/TA responses as training
trajectories.  Those responses are useful for prompt mining and diagnostics, but
Gated-GRPO updates should use rollouts generated by the current gated policy.

## Recommended first experiment

Build or locate the OP-VEC mode manifest first:

```bash
python scripts/modes/build_opvec4_modes.py \
  --config configs/gated_grpo.yaml
```

Then run a small on-policy coefficient experiment:

```bash
python scripts/train/opvec_gated_grpo_loop.py \
  --config configs/gated_grpo.yaml \
  --mode-manifest /tmp/shared-storage/OnPolicy/modes/opvec4/mode_manifest.json \
  --run-dir /tmp/shared-storage/OnPolicy/runs/gated_grpo/global_150_seed20260510 \
  --seed-manifest /tmp/shared-storage/OnPolicy/data/frontier150_prompts.jsonl \
  --num-iters 2 \
  --num-prompts 150 \
  --samples-per-prompt 8 \
  --gate-parameterization global \
  --max-new-tokens 512 \
  --max-logprob-tokens 3072 \
  --lr 0.01 \
  --prior-loss-weight 0.02 \
  --max-coefficient-delta-from-init 0.20 \
  --frontier-task-quota tool=64 \
  --frontier-task-quota code=64 \
  --frontier-task-quota memory=32 \
  --task-weight tool=1.5 \
  --task-weight code=1.5 \
  --task-weight memory=0.5
```

If you want to start from a known TA/cg gate checkpoint:

```bash
  --init-gate-checkpoint /path/to/fixed075_or_cg.gates.json
```

For an inexpensive command sanity check:

```bash
python scripts/train/opvec_gated_grpo_loop.py \
  --config configs/gated_grpo.yaml \
  --mode-manifest /tmp/shared-storage/OnPolicy/modes/opvec4/mode_manifest.json \
  --run-dir /tmp/shared-storage/OnPolicy/runs/gated_grpo/dryrun \
  --num-iters 1 \
  --num-prompts 2 \
  --samples-per-prompt 2 \
  --max-gated-modules 1 \
  --dry-run
```

## Output layout

Each iteration writes:

```text
iter_001/rollouts.jsonl

iter_001/gate_updates.jsonl
iter_001/gate_updates.summary.json
iter_001/gate_updates.gates.json
```

The loop-level audit file is:

```text
gated_grpo_loop_manifest.json
```

Use the final gate checkpoint to bake a standard HF checkpoint:

```bash
python scripts/eval/opvec_bake_checkpoint.py \
  --config configs/gated_grpo.yaml \
  --mode-manifest /tmp/shared-storage/OnPolicy/modes/opvec4/mode_manifest.json \
  --gate-checkpoint /tmp/shared-storage/OnPolicy/runs/gated_grpo/global_150_seed20260510/iter_002/gate_updates.gates.json \
  --output /tmp/shared-storage/OnPolicy/checkpoints/gated_grpo_global_150
```

Or pass `--bake-final` to `opvec_gated_grpo_loop.py`.

## How to interpret the learning signal

For each prompt, the collector samples `K` responses from the current gated
policy and stores `old_logprob` under the same gate checkpoint.  The updater
computes group-relative advantages:

```text
A_i = (reward_i - mean(reward_group)) / std(reward_group)
```

Then it computes a clipped GRPO/PPO sequence loss over the new log-probability
under the current gate parameters.  Since the LM weights are:

```text
W(alpha) = W_base + sum_i alpha_i * Delta_i
```

PyTorch can backpropagate token log-probability gradients into `alpha`; all base
model parameters are frozen.

Rows with no within-group reward variance contribute no policy gradient.  This
is expected and should be measured, not hidden.

## Practical defaults

Start with `--gate-parameterization global`.  It trains only three effective
expert strengths and is much less likely to overfit than parameter-level gates.
After it gives a real heldout trend, move to `layer-band`; reserve
`global-parameter` for analysis or larger calibration pools.

Use strong trust-region settings at first:

```text
--prior-loss-weight 0.02
--max-coefficient-delta-from-init 0.20
```

Memory is currently better treated as a retention constraint when the prompt set
is saturated.  Tool/Code should provide most of the frontier signal.

## VeRL notes

The recommended first-line training path is still the OP-VEC-native loop above,
because it is auditable and writes gate checkpoints directly.  The repository
also includes a VeRL compatibility path:

```text
scripts/frameworks/opvec_prepare_verl_data.py      # prompt parquet/jsonl builder
scripts/frameworks/opvec_verl_reward_fn.py         # custom reward hook
scripts/frameworks/opvec_verl_external_lib.py      # experimental actor patch
configs/verl_gated_grpo_experimental.yaml          # config skeleton
```

The external-lib hook freezes the base LM, attaches `model.opvec_gate_manager`,
and installs OP-VEC gated linears immediately after VeRL loads the HF actor.
This is intentionally labeled experimental because VeRL internals can change
between releases.  If it becomes brittle, keep using the native loop and port
only the reward/data side to VeRL.

Minimal environment for the VeRL hook:

```bash
export OPVEC_ENABLE_VERL_PATCH=1
export OPVEC_CONFIG=$PWD/configs/gated_grpo.yaml
export OPVEC_MODE_MANIFEST=/tmp/shared-storage/OnPolicy/modes/opvec4/mode_manifest.json
export OPVEC_GATE_PARAMETERIZATION=global
export OPVEC_MAX_GATED_MODULES=0
export OPVEC_FREEZE_BASE=1
```

The config skeleton should be treated as a starting point for your cluster/VeRL
version, not as a guaranteed universal launcher.
