# 2026-05-15 OP-VEC 动态损失缩放实验中文报告

## 一句话结论

5 月 15 日这组实验证明：**gate 能被推起来，proxy reward 也能接近 5 月 14 日 best，但当前训练信号主要沿 memory-only 方向推动，没有复现 5 月 14 日 best 的 code+memory 分离结构**。当 memory gate 均值进入 `~0.60` 区间后，E/F/G/H 都出现或预测到 Tool 崩溃。因此问题不是“梯度太小”或“系数推不动”，而是**训练信号方向不对**。

后续原则：不能为了让系数落到某个期望区间去调 LR、cap、OPD target；主线必须控制训练信号本身，包括 OPD 样本构成、任务方向配比、all-success preservation 和 per-task gradient contribution。

## 实验目标

本轮目标是从 `1/3` task-vector checkpoint 出发，用 96 条 paper96 calibration prompts 训练 OP-VEC gate，并监控三件事：

| 目标 | 具体问题 |
|---|---|
| reward 是否提升 | Tool/Memory/Code 三任务 proxy reward 是否一起上升 |
| task vector 是否被有效推动 | gate 是否离开 `1/3`，尤其能否进入 0.5-0.8 能力区间 |
| 是否泛化到正式评测 | candidate checkpoint 是否能在 Eval6 的 BFCL / HotpotQA / CURE 上保持或提升 |

实验中使用动态 OPD：每轮从当前 policy 的 all-fail prompt 中找 expert 能做对的轨迹，构造 distillation loss；对 all-success prompt 使用 NLL preservation；对有 reward 方差的 prompt 使用 GRPO/frontier loss。

## 当前实现逻辑

| 模块 | 当前行为 | 作用 |
|---|---|---|
| GRPO/frontier | 官方 reward，row-centered group advantage，`PPO_LOSS_WEIGHT=6.0` | 利用同一 prompt 下不同 rollout 的 reward 差 |
| Dynamic OPD | policy 全错、expert 可恢复时加入 expert positive + policy negative | 给全错样本提供可学习方向 |
| Retention | all-success row 上做 NLL preservation | 保持当前已经成功的行为 |
| Dynamic scale | 先 no-grad 估计 OPD/retention loss，再缩放到目标区间 | 解决不同任务 NLL 长度差异导致的量级问题 |
| Optimizer | SGD，epoch-scope update | 每轮 rollout 后累计一轮梯度再更新 gate |

关键实现开关：

```text
--opd-dynamic-scale
--opd-task-balanced-loss-scale
--retention-dynamic-scale
--retention-task-balanced-loss-scale
--retention-scale-target
```

## 最重要的失败模式

### 1. Gate 不是推不动，而是推错方向

A/B/C/E/F/G/H 都能移动 gate；失败原因不是梯度消失。真实模式是：

```text
dynamic OPD 先修 Tool
-> Tool 很快饱和
-> 剩余 all-fail recoverable 样本变成 memory-heavy
-> OPD/GRPO/retention 的净方向主要推 memory
-> code 基本留在 1/3 附近
-> memory 到 ~0.60 后 Tool 行为崩溃
```

这说明 dynamic scale 只保证各任务 loss 幅度接近，但没有保证每轮可用信号的任务方向均衡。

### 2. `memory ~= 0.60` 是经验风险边界，不是目标区间

多个 run 独立复现同一现象：

| Run | 进入风险前最好点 | 后续 gate | 后果 |
|---|---|---|---|
| E | iter9 proxy: Tool `0.9555`, Memory `0.8125`, Code `0.4066` | memory `0.6054` | iter10 Tool `0.2755` |
| F | iter8 proxy: Tool `0.9711`, Memory `0.7891`, Code `0.4346` | memory `0.6065` | iter10 partial Tool `0.3321` |
| G | iter8 proxy: Tool `0.8835`, Memory `0.7969`, Code `0.4316` | memory `0.6211` | iter9 Tool `0.0569` |
| H | iter9 proxy: Tool `0.9602`, Memory `0.7812`, Code `0.4336` | memory `0.6055` | 停止，避免重复已知 collapse |

这个边界只能作为诊断，不应该作为调参目标。不能通过 hard cap 把 memory 卡在 `0.57` 来“制造成功”，因为那不是训练信号学出来的结构。

### 3. Retention 只能延缓崩溃，不能决定方向

当前 retention 是 all-success NLL preservation。它能让成功样本的输出不要立刻坏掉，但它不会告诉优化器：

```text
memory 再涨会破坏 tool
code 应该被单独推到更高区间
tool 的能力应该通过哪个 gate geometry 保持
```

因此 retention 是 preservation，不是 task-vector trust region，也不是任务方向控制器。

## 为什么这不是“调 LR 就能解决”

LR、momentum、OPD target、max coefficient delta 只能控制步幅，不能改变方向。如果训练信号本身后期变成 memory-heavy，那么：

```text
小 LR: 慢一点走向 memory-only
大 LR: 快一点过冲到 Tool collapse
cap: 人为停在 collapse 前，但不是学习出来的最优组合
```

所以用户指出的原则是正确的：**不能对着期望结果调参，核心是控制训练信号**。

## 下一步正确方向

下一轮实验不应继续围绕 `memory~0.57`、`LR=多少`、`cap=多少` 做搜索，而应固定优化超参，改训练信号：

## Code OPD positive threshold 审计

用户提出的高优先级疑点：

```text
CodeRewardAdapter: success = score >= 0.95
DYNAMIC_OPD_POSITIVE_THRESHOLD = 1.0
OPD_POSITIVE_REWARD_THRESHOLD = 1.0
```

代码层面这个疑点成立：

- [opvec/rewards/simple.py](/mnt/cache/wuruixiao/users/lsc/Agent/ExpertGym/opvec/rewards/simple.py:183)：public examples 全过时会把 score 至少抬到 `0.95`。
- [opvec/rewards/simple.py](/mnt/cache/wuruixiao/users/lsc/Agent/ExpertGym/opvec/rewards/simple.py:191)：code success 判定是 `score >= 0.95`。
- [scripts/data/build_opd_distill_from_expert_rollouts.py](/mnt/cache/wuruixiao/users/lsc/Agent/ExpertGym/scripts/data/build_opd_distill_from_expert_rollouts.py:175)：dynamic OPD builder 用 `reward_train >= positive_threshold` 选择 expert positive。
- [scripts/train/opvec_update_gates_from_rollouts.py](/mnt/cache/wuruixiao/users/lsc/Agent/ExpertGym/scripts/train/opvec_update_gates_from_rollouts.py:2630)：update 侧 OPD positive/negative 也按 `reward_train` threshold 切分。

但对本次 paper96 实验，统计结果显示它不是 code 没被推动的主因：

| 检查项 | 结果 |
|---|---:|
| code expert prompts | `32` |
| code expert samples | `64` |
| `reward_train=1.0` samples | `24` |
| `success=True` samples | `24` |
| `success=True 且 reward_train<1.0` | `0` |
| `reward_train=0.95` samples | `0` |
| expert positive prompts, threshold `1.0` | `17` |
| expert positive prompts, threshold `0.95` | `17` |

逐轮反事实也一致：对 E/F/G/H 的 code all-fail rows，`threshold=1.0` 与 `threshold=0.95` 得到的 recoverable code prompt 数完全相同。因此把阈值从 `1.0` 改成 `0.95`，不会增加这次 paper96 的 code OPD positive。

真正限制 code OPD 的原因更像是：

1. 当前 32 个 code prompts 中，expert 在 `threshold=1.0` 下只覆盖 17 个 prompt。
2. 每轮 policy all-fail 的 code prompt 未必落在这 17 个 expert-positive prompt 上。
3. 因此大量 code all-fail 被跳过，不是因为 expert 是 `0.95`，而是因为 same-prompt expert 本身没有达到 positive threshold。
4. 当前 policy/code OPD 样本整体也没有 `reward_train=0.95`：policy code samples 中 success_true 全部出现在 `reward_train=1.0`，OPD code positive 也全部是 `1.0`。

判断：

- **短期不建议仅把 code positive threshold 从 `1.0` 改到 `0.95`，因为对当前 paper96 数据无效。**
- 这个 mismatch 仍然是未来数据管线的隐患：如果后续 code prompt 没有 source tests，只能靠 public examples fallback，那么 success=True 可能对应 `reward_train=0.95`，届时 `threshold=1.0` 会错误丢掉 code expert positive。
- 更原则化的修复不是盲目降全局阈值，而是让 OPD builder 支持 `success == true` 或 task-specific positive threshold，并在 summary 中显式记录 `positive_by_success` / `positive_by_reward_threshold`。

### 1. OPD after-filter task balance

现在的问题是“采样前 balanced，过滤后不 balanced”。应记录每轮 OPD 最终进入 loss 的任务计数，如果 memory 过多、code/tool 不足，就宁可减少 OPD 总量，也不要让 memory 自动填满预算。

建议规则：

```text
每轮每任务最多 K 条 OPD
某任务不足 K 条则缺失，不用其他任务补齐
记录 selected / candidate / skipped 原因
```

### 2. 分离 repair 与 preservation

| 信号 | 样本 | 作用 |
|---|---|---|
| OPD repair | current all-fail + expert success | 修复当前 policy 完全不会的能力 |
| NLL preservation | all-success policy trajectory | 保持已经会的行为 |
| GRPO frontier | 同 prompt 内 reward 有方差 | 利用 on-policy preference |

不能用 memory repair 信号替代 code/tool preservation，也不能让 all-fail 的任务分布决定全部更新方向。

### 3. 记录 per-task gradient contribution

在 step 前输出：

```text
grad_norm_by_loss = {
  grpo/tool, grpo/memory, grpo/code,
  opd/tool, opd/memory, opd/code,
  retention/tool, retention/memory, retention/code
}
```

如果某轮 `opd/memory` 占主导，应在更新前就判定训练信号不可用，而不是等下一轮 Tool collapse 后才知道。

### 4. 补 code-positive 信号

5 月 14 日 best 的关键是 code gate 被推到 `~0.71`。当前 dynamic OPD 里 code recoverable 样本太少，导致 code 长期留在 `~0.34`。下一步需要从同一 calibration pool 里构造更高信息量的 code-positive rows，但必须清楚标注来源，不能混成不可追溯数据。

### 5. 用 Eval6 决定 checkpoint，不用 proxy 单独决策

paper96 proxy 会因 Tool 饱和和 Memory 提升而显得很高，但这不保证 gate geometry 正确。正式报告应以 BFCL / HotpotQA / CURE 三项为准。

正确 strategy 名称：


- 由于 iter-2 reward 已经下降，尤其 code 从 `0.4711` 降到 `0.3545`，这个 run 不值得继续送正式 Eval6。它的价值是诊断：在当前信号构造下，`parameter` 更贵，但没有快速形成有用的局部分工。

## 最终判断

本轮实验的科研价值很明确：

1. 证明 OP-VEC gate 优化有信号，不是完全学不动。
2. 证明 dynamic OPD scale 能修复 loss 量级问题。
3. 发现了稳定复现的 failure mode：dynamic all-fail OPD 会后期 memory-heavy，导致 memory-only gate movement。
4. 发现 formal Eval6 与 proxy 不完全一致：E/F 的 Code 正式指标并没有坏，但训练过程仍不是可靠收敛。
5. 下一步论文故事应从“怎么把系数调到好区间”转为“如何设计 on-policy training signal，让 GRPO/OPD 自动发现有效 task-vector 组合”。

因此，5 月 15 日实验不是最终成功，但它把问题定位清楚了：**不是优化器问题，核心是训练信号的任务方向、可恢复样本分布和 credit assignment。**
